Governance

Open governance, written down.

Waqt is a standard first and software second. Its rules are versioned, and every change to them goes through a proposal and a decision record. This page keeps project roles, formal decisions and ratification status clearly apart.

People

Project role information

DEMO · EDITABLE PROJECT METADATADemo metadata — editable before public release.

Role information says who currently fills which role. It is not a governance decision and does not ratify anything. Waqt welcomes qualified experts and contributors.

Ratification status

Decision records ratified · contract not yet released

All 9 decision records state ratification by a named maintainer (Dr. Salim Muhammed Redi). The repository holds no signed artifact for it, and ratifying decisions is not a release: the contract is version 2.0.0 (draft — not released), the independent-implementation reviewer role is unfilled, and open specification questions remain open.

Three different things

  • Project role information — demo, editable metadata (above).
  • Formal governance decisions — the decision records below, read from the repository.
  • Ratification status — read from the decision records; separate from the contract's release status.

Formal governance decisions

DR-0001RATIFIED

Day label: civil date of the closing Maghrib instant

Accepted 2026-10-04 · contract 2.0.0 · requirements: DAY-004, DAY-007, DAY-009

Context

SEMANTICS section 3 and CALENDAR-INTEROP section 1 already said the label is the Gregorian civil date on which the closing Maghrib falls. The reference nevertheless took the label from the solar-date key handed to its solver, which differs from the civil date wherever the zone's offset is far from the longitude's …

DR-0002RATIFIED

Event assignment and undefined bounding Maghribs

Accepted 2026-10-04 · contract 2.0.0 · requirements: EVT-004, UND-001

Context

Two choices were shared by both implementations and so could never be exposed by comparing them: which date an event after local midnight belongs to, and what happens to a day when exactly one of its bounding Maghribs is undefined.

DR-0003RATIFIED

next_event is by occurrence

Accepted 2026-10-04 · contract 2.0.0 · requirements: EVT-007

Context

/v1/waqt returned the first listed event after the instant, in list order. After Maghrib the previous solar day's Isha is not in the current listing, so tonight's Isha (about 65 minutes away) was skipped and tomorrow's Fajr reported. SCHEDULING already used occurrence semantics, so the two layers disagreed.

DR-0004RATIFIED

Asr: declination convention and undefined rule

Accepted 2026-10-04 · contract 2.0.0 · requirements: AST-001, AST-002

Context

Both implementations evaluated the Sun's declination at the upper transit to obtain the noon shadow, but nothing said so, and Sprint 15 measured that the alternative convention would move Asr by up to 5.9 s, more than the 5 s band. DR-0005RATIFIED

arithmetic-tabular: leap pattern and identity

Accepted 2026-10-04 · contract 2.0.0 · requirements: CAL-002

Context

Several tabular patterns exist. Both implementations used the civil pattern, so no comparison could expose the choice. The year lengths were vectors but not prose.

DR-0006RATIFIED

Errors for non-existent Hijri dates and unknown time zones

Accepted 2026-10-04 · contract 2.0.0 · requirements: CAL-004, ERR-002

Context

to-gregorian for 1448-02-30 returned 2026-08-15 (a different month) and year 0 returned 0621-07-30; an unknown timezone_override surfaced as HTTP 500 INTERNAL_ERROR (COP: never acceptable for bad input).

DR-0007RATIFIED

Umm al-Qura: range, chain, and what stays unresolved

Accepted 2026-10-04 · contract 2.0.0 · requirements: CAL-011 (resolved); CAL-007 (open)

Context

The reference answered for 1650-2300 and failed obscurely outside; the independent implementation answered 1700-2300 with OUT_OF_RANGE. The chain origin was unstated. Test inputs (limb, refraction, elevation, algorithms) were unstated.

DR-0008RATIFIED

Scheduling rules that lived only in vectors

Accepted 2026-10-04 · contract 2.0.0 · requirements: SCH-009, SCH-010, SCH-011, SCH-012, SCH-013

Context

A clean-room implementation written from SCHEDULING.md alone passed 108 of 116 vectors; the 8 failures were rules stated nowhere in prose.

DR-0009RATIFIED

The default Hijri calendar provider of the HTTP API is umm-al-qura (API 1.7.0)

Accepted 2026-10-10 · contract 2.0.0 · requirements: none. No requirement in contract 2.0.0 defines a default Hijri provider (searched spec/requirements.json); this is an API-level decision.

Context

Until API 1.6.0 a request that omitted calendar_provider was served by arithmetic-tabular. The project owners (Dr. Salim Muhammed Redi and Mr. Hawas Muhaba Hussein) chose Option B: the default becomes umm-al-qura.

Lifecycle

How the specification changes

  1. 01

    ProposeAnyone may open a change proposal: the question, evidence, proposed text and vectors.

  2. 02

    EvidenceMeasurements from independent implementations — or a stated reason only one exists.

  3. 03

    ReviewAt least one reviewer who is not the author; open for a minimum period.

  4. 04

    DecideA decision record is written; dissent is recorded in the dissenter’s words; a named maintainer ratifies.

  5. 05

    ChangeRequirement, vectors and prose change together, with a changelog entry.

Standard

Principles and status

  • Written requirements govern; test vectors illustrate.
  • Facts are normative; conventions are configurable — astronomy is fixed; Hijri providers and Fajr/Isha angles are choices you pass in.
  • A clean report is not a goal. Open questions stay open until genuinely settled.
  • Temporal facts, not religious rulings.
