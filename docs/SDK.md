# SDKs & Language Bindings (Sprint 9)

Official thin SDKs over the documented `/v1/*` HTTP/JSON contract:

```
Waqt Specification
       |
   HTTP / JSON
       |
 ┌───────────────┐
 │ Python SDK    │   sdks/python/  — package "waqt-client"
 │ JS/TS SDK     │   sdks/js/waqt-client/  — package "waqt-client"
 └───────────────┘
       |
 Applications
```

**The important word is thin.** Neither SDK computes a Maghrib instant, a
Hijri date, or a scheduling result. Every value either SDK returns came
from a live `/v1/*` HTTP response, parsed into an ergonomic
language-native type. Neither SDK is "another implementation of Waqt's
rules" — that is precisely the property `sdks/vectors/` conformance
tests exist to keep true (see "Conformance" below).

## Two SDKs, one contract

| | Python (`sdks/python/`) | JavaScript/TypeScript (`sdks/js/waqt-client/`) |
|---|---|---|
| Package name | `waqt-client` | `waqt-client` |
| Sync client | `WaqtClient` (`httpx.Client`) | — (see below) |
| Async client | `AsyncWaqtClient` (`httpx.AsyncClient`) | `WaqtClient` (`fetch`, promise-based) |
| Types | `@dataclass` | Plain frozen objects + parse functions, typed via JSDoc + hand-written `index.d.ts` |
| Escape hatch for un-wrapped endpoints | `client.request(method, path, params=..., json=...)` | `client.request(method, path, { params, json })` |
| Error type | `WaqtApiError` (`.code`, `.message`, `.details`, `.status_code`) | `WaqtApiError` (`.code`, `.message`, `.details`, `.statusCode`) |
| Version negotiation | `WaqtClientConfig.on_version_mismatch` | `config.onVersionMismatch` |

JavaScript ships one client, not two, because JavaScript's networking
primitives (`fetch`, Node's HTTP stack) are inherently non-blocking —
there is no idiomatic synchronous HTTP call to wrap. A single
promise-based client **is** "synchronous/asynchronous requests where
appropriate" for that language; Python's two classes are the same
principle applied where the language actually has both idioms. See
`sdks/js/waqt-client/README.md#why-async-only`.

Both SDKs' method names track the same endpoints 1:1 (`get_waqt` /
`getWaqt`, `schedule_snapshot` / `scheduleSnapshot`,
`institutional_week` / `institutionalWeek`, ...) so a developer who has
used one recognizes the other immediately.

## API client behavior

Both SDKs provide, per the Sprint 9 brief:

- **Sync/async requests where appropriate** — see table above.
- **Configurable base URL and timeout** — `WaqtClientConfig`/config object.
- **Timeout handling** — both raise `WaqtTransportError` on timeout
  (`httpx.TimeoutException` / `AbortController`-driven abort), distinct
  from a server-issued `WaqtApiError`.
- **Structured error handling** — every non-2xx response is parsed into
  the documented `{code, message, details}` shape (docs/API.md) and
  raised as `WaqtApiError`, never a bare HTTP-status exception.
- **Serialization/deserialization** — every typed method parses the
  server's JSON into a language-native type; nothing is left as a raw
  dict except the deliberately-generic `SchedulingResult`/
  `InstitutionalCalendarResult` types (see "Design decisions" below) and
  the `.raw`/`.raw` field every type carries for forward compatibility.
- **Version negotiation** — both SDKs read `meta.api_version` off every
  response and compare it against the SDK's declared supported range
  (`config.py`/`config.mjs`), configurable as ignore/warn/raise.
- **Provider/profile selection** — `calendar_provider`/`calendarProvider`,
  `fajr_angle`/`fajrAngle`, `isha_angle`/`ishaAngle`,
  `asr_ratio`/`asrRatio` are accepted both as per-call arguments and as
  client-level defaults (`WaqtClientConfig.default_*` /
  `config.default*`), with per-call always winning.

## Local vs server computation

Both SDKs are **remote Waqt API clients**. Neither should be read as
"Python/JS SDK = Waqt itself" — a **local Waqt computation library** (the
astronomical/calendar engine embedded directly, no network round-trip) is
a distinct, separately-specified component. The Sprint 9 brief is
explicit that this can come later or be separately specified; nothing in
either SDK here pretends to be that library. (Parallel Milestone A's
`independent-astronomy/` — see docs/INDEPENDENT-ASTRONOMY.md — is a
second *server-side reference implementation* used for cross-validation,
not a client-embeddable library either; it is not wired into either SDK.)

## Conformance

`sdks/vectors/sdk_conformance_vectors.json` holds real, captured `/v1/*`
HTTP responses (generated by
`sdks/vectors/generate_sdk_conformance_vectors.py` calling the live
FastAPI app — nothing hand-typed), covering:

- Every response shape both SDKs model (`/v1/waqt` ordinary + `UNDEFINED`
  + non-default profile, `/v1/day`, `/v1/events`, `/v1/hijri` under two
  providers, `/v1/calendar`, `/v1/location`, `/v1/conversions` both
  directions, `/v1/calendar/convert` both directions,
  `/v1/calendar/boundary-crossing`, `/v1/schedule/{snapshot,span}`,
  `/v1/institutional/{week,profile}`).
- Three error envelopes (`INVALID_INSTANT` 400, `INVALID_SPAN` 400,
  `VALIDATION_ERROR` 422).

Both SDKs' own test suites (`sdks/python/tests/test_conformance.py`,
`sdks/js/waqt-client/test/conformance.test.mjs`) parse this **same
file** with their own, independent parsing code and assert the same
facts about the result. This is what "the Python and JavaScript SDKs
implement the same Waqt API contract" means operationally, not just "they
both happen to call the server" (the exact distinction the Sprint 9
brief draws).

Each SDK additionally has a live-server integration test suite hitting
a real running instance of the FastAPI app end to end
(`sdks/python/tests/test_client_{sync,async}.py`,
`sdks/js/waqt-client/test/client.test.mjs`) — genuine HTTP, not mocked.

## Running the tests

```bash
# Python
cd sdks/python && pip install -e ".[dev]" && pytest -q

# JavaScript
cd sdks/js/waqt-client && npm test
```

## Design decisions

- **`SchedulingResult`/`InstitutionalCalendarResult` are deliberately
  generic**, not one dataclass per endpoint variant. `/v1/schedule/*`
  and `/v1/institutional/*` each cover several distinct response shapes
  (docs/SCHEDULING.md, docs/INSTITUTIONAL.md); modeling every one
  precisely would mean re-deriving Waqt's own scheduling/institutional
  logic in two more languages just to know which fields exist when —
  exactly what "the SDK should not become another implementation of
  Waqt's rules" rules out. Both types keep the one or two fields every
  variant shares typed, and the full response on `.raw`.
- **Every type keeps `.raw`** (Python) / has parse functions that never
  drop unrecognized fields into an opaque bucket that hides them
  (JavaScript's `.raw`) so a field either SDK's dataclass/type hasn't
  caught up to modeling yet is still reachable without waiting for a new
  release.
- **No retries, no caching, no client-side rate limiting.** A thin SDK
  passes requests through; adding retry/backoff policy would be a
  meaningful behavioral decision this SDK isn't positioned to make for
  every caller (a caller doing a bulk historical backfill wants
  different retry behavior than one serving a live prayer-times widget).
  Left to the caller, or a future explicit opt-in.

## Honest limitations

- **Not every endpoint has a fully-typed response.** `/v1/schedule/*`
  and `/v1/institutional/*` (except `week`) return their full JSON on
  `.raw`/`raw` with only the fields common to all variants explicitly
  typed — see "Design decisions" above for why.
- **`/v1/schedule/resolve` and the two `.../resolve` institutional
  endpoints take a raw request body**, not a typed request object. Their
  request shapes are richer and more varied than a `GET`'s query
  parameters (docs/SCHEDULING.md, docs/INSTITUTIONAL.md); typing them
  fully is future SDK work, not attempted here.
- **No retry/backoff, no connection pooling tuning exposed, no request
  caching.** See "Design decisions" above.
- **The JS SDK's live integration tests spawn a real `python3 -m
  uvicorn` subprocess.** This means the JS test suite has an implicit
  Python + the repo's own dependencies as a test-time requirement; it is
  not needed to *use* the JS SDK, only to run its own integration tests.
- **Neither SDK has been published to PyPI/npm** — both are installed
  from the checkout (`pip install -e sdks/python`,
  `npm install ./sdks/js/waqt-client`) for this sprint. Publishing is a
  packaging/release-process step, not an SDK-design one, and is left for
  a deliberate follow-up rather than assumed here.
