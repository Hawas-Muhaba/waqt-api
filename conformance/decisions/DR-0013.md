## Context
The merged change added `calendar_error` to `/v1/calendar/convert` and fixed a 500 inside contract 1.7.0; DR-0011 and DR-0012 add observable behaviour (422 for invalid profile
parameters; a null Hijri label for out-of-range dates). `API_VERSION` was still 1.7.0. The service is deployed; external use of 1.7.0 is unknown (no tags, no usage data).

## Decision
The next release's API contract is **1.8.0**; the `/v1` URL namespace is retained (no response shape is broken). The project does **not** claim that 1.7.0 had no external consumers.
1.7.0 artifacts and historical vectors are preserved. Migration instructions: `docs/migrations/API-1.8.0-validation-and-out-of-range.md`.

## Evidence
Repository search: no git tag, no `conformance/releases/` manifest, no published immutable artifact conflicts with this plan (checked locally and with `git ls-remote --tags`).
The project owner states (2026-10-11, in the review session) that no package has been published to any registry and that there is no public live deployment. That is the owner's statement; it was not independently verified, and it does not establish that nobody consumed 1.7.0 (private or local use is unknown). 1.8.0 is kept as the conservative choice.

## Consequences
`API_VERSION`, `docs/VERSIONING.md`, `docs/API.md`, SDK `MAX_KNOWN_API_VERSION`, tests and the migration record reference 1.8.0. Package versions (waqt-core 0.5.0, waqt-api 0.5.0, ...) are
NOT bumped here: that is a release step.

## Alternatives considered
Keep 1.7.0 (rejected: it assumes nobody consumed it). 2.0 / `/v2` (rejected: no response shape is broken).

## Dissent and unresolved points
None recorded. Open: ratification evidence and independent review (see GOVERNANCE.md).

## Reopen when
Evidence shows 1.7.0 was never distributed, or a response-shape break is needed.
