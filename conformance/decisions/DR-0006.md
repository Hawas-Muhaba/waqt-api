## Context
`to-gregorian` for 1448-02-30 returned 2026-08-15 (a different month) and year 0 returned 0621-07-30; an unknown `timezone_override` surfaced as HTTP 500 `INTERNAL_ERROR` (COP: never acceptable for bad input).

## Decision
CAL-004: a Hijri date that does not exist is rejected with `INVALID_HIJRI_DATE` (HTTP 400): year < 1, or a day beyond the month's length in that provider (checked by round trip for any provider). Out-of-range month/day numerals (outside 1-12 / 1-30) may instead be `VALIDATION_ERROR`, because shape validation precedes calendar validation. ERR-002: an unknown IANA zone is `UNKNOWN_TIMEZONE` (HTTP 400) with `details.parameter/received/expected`; no other code is acceptable. The zone is validated when the provider is constructed, so every endpoint, the batch path and `waqt_local` behave identically.

## Evidence
Reproduced through the real endpoints before the fix (200 with a wrong date; 500). After: `1448-2-30`, `0-1-1`, `-5-1-1`, `1448-12-30` are 400 `INVALID_HIJRI_DATE`; `1447-12-30` (leap) converts; `Mars/Base` and `../etc/passwd` are 400 `UNKNOWN_TIMEZONE`; `waqt_local` raises the matching exceptions. The institutional `month_days` helper, which relied on normalisation to find month length, was adapted.

## Consequences
Additive error codes (API 1.6.0). Narrowing the accepted code set of `err/tz-unknown` from three codes to one is a **breaking** change to the conformance contract and is why it is 2.0.0 (conformance/VERSIONING.md); the independent implementation had to change.

## Alternatives considered
Reuse `VALIDATION_ERROR` for both: rejected, a dedicated code lets clients react and follows `UNKNOWN_CALENDAR_PROVIDER`.

## Configurability (religious / regional conventions)
Not a convention question.

## Dissent and unresolved points
None.

## Reopen when
A client library needs finer-grained codes (additive).
