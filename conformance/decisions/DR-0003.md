## Context
`/v1/waqt` returned the first *listed* event after the instant, in list order. After Maghrib the previous solar day's Isha is not in the current listing, so tonight's Isha (about 65 minutes away) was skipped and tomorrow's Fajr reported. SCHEDULING already used occurrence semantics, so the two layers disagreed.

## Decision
`next_event` is the chronologically earliest event strictly after the instant, over the current day's listed events plus the previous solar day's Isha. `events` (the listing) is unchanged.

## Evidence
Addis Ababa 2026-09-19T15:42:00Z (Maghrib 15:22 UTC): before, `fajr` in 10:22:52; after, `isha` in 00:46:28, which matches vector `next-event/tonights-isha` (16:28:28). Stepping through a day at 15-minute intervals yields the cycle asr, maghrib, isha, fajr, sunrise, dhuhr, asr.

## Consequences
Behaviour change in `waqt-core` 0.4.0 / API 1.6.0. The two SDK recorded vectors that had captured the old value (`/v1/waqt` and `/v1/events` at that instant) were updated; only `next_event` fields changed.

## Alternatives considered
Keep listing semantics and document them: rejected, it reports an event that is not next.

## Configurability (religious / regional conventions)
Not configurable: which event is next is a fact, not a convention.

## Dissent and unresolved points
None.

## Reopen when
A product need for 'next event of the current listing' as a separate field (additive).

## Vectors affected
day-model: next-event/tonights-isha promoted from open-questions; recorded SDK vectors #0 and #4 updated.
