## Context
This resolves the open point recorded in DR-0009 ("whether `waqt-core`'s internal fallback should follow the API default"). DR-0009 is not edited (records are append-only). DR-0009 made `umm-al-qura` the default of the HTTP API (API 1.7.0). The lower layers still defaulted to `arithmetic-tabular`: `waqt-core` (`calendar_interop`, `SchedulingContext`), the COP (silent: both conformance adapters chose `arithmetic-tabular`), `waqt-local` and the CLI. A caller that omitted the provider therefore got a different Hijri label depending on the layer they entered through.

## Decision
One default, defined once in `waqt-core` (`waqt_core.calendar_providers.default`), read by the API, `waqt-local` and the CLI; and stated in the contract as CAL-012: **an omitted provider means `umm-al-qura`; an explicit provider is always honoured.** The default labels days only and never changes a Waqt instant. COP inputs `provider` / `calendar.provider` / `calendar_provider` become optional. The independent implementation states the same default in its own `defaults.mjs` (it never imports the reference).

## Evidence
Reference and independent implementation pass all normative vectors after the change (708 and 711 normative passes, 0 failures). Only three normative vectors depended on the old implicit default; all assert the provider-independent DAY-004 label rule, so their **expected values are unchanged** and the provider they always meant (`arithmetic-tabular`) is now named in their input. Seven new `exact` vectors (`calendar-default.json`) copy their expected values from existing normative Umm al-Qura vectors (the official 1 Muharram dates 1438 and 1447) with the provider omitted, plus two label vectors on 1 Muharram 1447. **Not measured:** other implementations of the contract (there are two); whether external consumers call the COP without a provider.

## Consequences
Behaviour change for any `waqt-core` caller that passes no provider: the Hijri label follows `umm-al-qura`, and outside 1700-01-01..2300-12-31 it is empty with a `calendar_error` instead of arithmetic-tabular's label. `waqt-core` 0.5.0, `waqt-local` 0.6.0, `waqt-cli` 0.2.0, `waqt-api` 0.5.0 carry it. Fixed on the way: `represent_instant` and `/v1/calendar/convert` raised `AttributeError` / returned 500 for an instant outside that range (a Hijri failure must never fail a Waqt computation; same policy as `/v1/waqt`).

## Alternatives considered
Leave the COP silent and the library on `arithmetic-tabular`: rejected by the requester (two defaults for one project). Make the provider mandatory in the COP: not chosen; it would break every existing caller and vector.

## Configurability (religious / regional conventions)
Umm al-Qura is a deliberate project default, **not** a claim that every community follows one calendar convention. Every other provider stays selectable per call.

## Dissent and unresolved points
**OQ-CAL-1 (new, deferred):** with the default and an instant or date just outside the range, the reference returns the Waqt day with an empty Hijri label while the independent implementation returns `OUT_OF_RANGE`. The contract does not decide; two `open`-tier vectors record the disagreement (`default/out-of-range/...`). No consensus was forced (GOVERNANCE.md section 5). **Review of CCP-0001 by the independent-implementation reviewer is outstanding (role unfilled).**

## Reopen when
OQ-CAL-1 is decided, the default changes again, or a third implementation disagrees.

## Vectors affected
`day-model.json` (3 inputs pinned; no expected value changed), `calendar-default.json` (new, 7), `open-questions.json` (+2 open vectors). Audit trail: `tools/migrate_default_provider_option_b.py`.
