# DR-0014: Strict JSON request types and calendar-error compatibility

| | |
|---|---|
| **Status** | Implemented for API 1.8.0; independent review: NOT performed; maintainer ratification: PENDING (see DR-0015 for the owner-approved release exception). |
| **Date** | 2026-10-12 |
| **Scope** | `POST /v1/schedule/resolve`, `POST /v1/institutional/fiscal-year/resolve`, `POST /v1/institutional/academic-year/resolve` |

## Decision

JSON request bodies are validated according to JSON value types; the API does not coerce JSON strings or booleans into numbers. ERR-004 profile fields accept finite JSON numbers only: JSON strings (including `"18"`), booleans, and null are invalid and return `422 VALIDATION_ERROR`. Integer fields accept JSON integers, and `hijri_year` is a positive JSON integer. Invalid body values return a structured 4xx response, never a successful result or an unhandled type error.

Optional JSON body fields are omitted to select their defaults. Explicit `null` is rejected unless the field's own format documents it as nullable; scheduling interval `start` and `end` remain nullable to represent open interval endpoints. Numeric query parameters remain textual on the HTTP wire and continue to be parsed by their declared endpoint types.

## Compatibility

Numeric HTTP query parameters are parsed from their textual representation, so a value such as `fajr_angle=18` is accepted while malformed text such as `null` is rejected. This does not permit numeric strings in JSON request bodies.

The existing human-readable `calendar_error` response difference is retained: `/v1/waqt` returns `{provider, message}`, while `/v1/calendar/convert` returns a string. Both routes expose additive `calendar_error_code` (`OUT_OF_RANGE` or `CALENDAR_ERROR`) as the stable machine-readable mapping used by the conformance adapters. Normalizing the legacy `calendar_error` values themselves still requires a separate consumer-compatibility review and appropriate API versioning.

## Upper-range verification limit

The independent Node implementation stores instants as Number microseconds, exactly only while the count remains within JavaScript's safe-integer range (approximately through year 2255). Date-level vectors through 2300 do not establish instant-level conformance through 2300. No full-range instant-conformance claim is made; a second independent verification method is required before such a claim.

## Evidence

HTTP regression tests cover JSON null and numeric-string rejection, positive integer validation, institutional rule/location types, and the continued acceptance of numeric query-string values. The upper-range limitation is documented in `conformance/independent/README.md` and `verification/README.md`.
